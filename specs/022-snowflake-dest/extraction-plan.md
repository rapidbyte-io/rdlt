# Working document: sqlcore extraction plan (T003/T004)

Produced by a four-way structural survey of the postgres and duckdb
destinations plus the shared core, then synthesized under the
byte-identity constraint. Kept as the reference the increments execute
against; the binding verdicts are summarized in research.md D12.

# Extraction plan — T003 (ensure choreography) and T004 (session/commit protocol) into `rdlt-connector-sqlcore`

## 0. Verdict first

**Both extractions must be narrowed, and T004 must be narrowed hard.** The task's premise — that the two destinations share a *choreography* that can be lifted whole — holds for T003 at the level of **decisions** and fails at the level of **SQL text and execution**. For T004 it fails at the level of **execution structure**, for a reason that is a hard type-system fact, not a taste call.

Three findings that change the shape of both tasks:

1. **The third destination does not share the ensure statement program at all.** `specs/022-snowflake-dest/tasks.md:T009` and `data-model.md` (`Ensured(tables)` row) specify Snowflake's ensure as *describe-once, then emit `ADD COLUMN` only when the column is genuinely absent*, with **no indexes at all** (SD4: "merge without enforced constraints") and **all DDL strictly before any unit** (SD3). Postgres and DuckDB both emit blind `ADD COLUMN IF NOT EXISTS` for every column on every ensure. So the shared surface across three destinations is a *desired-state list*, never a statement list.
2. **The replay-branch outcome is inverted between the two existing destinations**, and inverted *for a structural reason*: pg (`DirectToTarget`) must `ROLLBACK` and return (`commit.rs:889-893`), DuckDB (`Staged`) must run the planner's `TruncateStage` program and `COMMIT` (`commit.rs:429-444`). This is not a spelling difference and it is not currently expressed anywhere in code — it lives in two long prose comments.
3. **A shared async execute skeleton cannot be written.** `DuckDbSession::commit` runs its entire body inside `with_conn(move |conn| …)` — a synchronous `FnOnce` holding a `MutexGuard<Connection>`, inside which `conn.transaction()` borrows `&mut Connection` for the guard's lifetime (`duckdb/src/dest/commit.rs:46-52, 364-446`). Postgres's is `async fn` over an owned `Client`. Snowflake's will be async. Unifying requires either an async trait in sqlcore (`async-trait` is **not** in `crates/rdlt-connector-sqlcore/Cargo.toml`, and contract **SM8** — recorded as a comment in that file — forbids sqlcore ever gaining a new external dependency) or restructuring DuckDB's concurrency model. Both are redesigns, not refactors.

Verified mechanically: **no test anywhere pins ensure DDL text.** `grep -rl "CREATE UNLOGGED\|ADD COLUMN IF NOT EXISTS\|GENERATED BY DEFAULT AS IDENTITY\|SET DATA TYPE"` over `crates/*/tests/` and `crates/*/src/` returns exactly the two source files and zero tests.

## 1. T003 — `crates/rdlt-connector-sqlcore/src/ensure.rs`

### What moves: the decision list. What stays: every byte of SQL.

sqlcore gains a **pure planner**, structurally the twin of `protocol::commit_script`: it returns *what must be true*, in order; each destination lowers that to statements in its own `ddl.rs`.

```rust
//! crates/rdlt-connector-sqlcore/src/ensure.rs

/// Which physical relation a step concerns.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Leg { Target, Stage }

/// The scd2 validity columns, in their frozen emission order.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Validity { From, To }

/// One ensure DECISION. The destination renders and executes; sqlcore owns
/// only the set and the order. `column` indexes `schema.columns`.
#[derive(Debug, Clone, PartialEq)]
#[non_exhaustive]
pub enum EnsureStep {
    /// This leg's relation must exist, carrying every column of `schema`.
    Table  { leg: Leg },
    /// This column must exist on this leg.
    Column { leg: Leg, column: usize },
    /// This column's type changed WITHIN this session and must widen.
    Widen  { leg: Leg, column: usize },
    /// An scd2 validity column on the TARGET only.
    Validity(Validity),
    /// A supporting index on the TARGET.
    Index(crate::plan::IndexSpec),
}

/// The facts the session supplies. `previous` is the schema this SESSION last
/// ensured — never the live catalog; that is what makes the widen predicate
/// session-scoped, and changing it is a behavior change, not a refactor.
pub struct EnsureCtx<'a> {
    pub previous: Option<&'a TableSchema>,
    pub full_load_publish: crate::protocol::FullLoadPublish,
}

/// Phase 1: the table DDL. Infallible — validation deliberately does NOT run
/// here, because today both destinations create the tables BEFORE validating
/// and a plan that validated first would move the failure point.
pub fn table_plan(schema: &TableSchema, mode: &WriteMode, ctx: &EnsureCtx<'_>) -> Vec<EnsureStep>;

/// Phase 2, run only after phase 1 has been APPLIED: the shared validators in
/// their frozen order, then the scd2 validity columns and the index plan.
/// Non-merge modes validate and return an empty program.
pub fn post_table_plan(
    options: &DestOptions,
    schema: &TableSchema,
    mode: &WriteMode,
) -> Result<Vec<EnsureStep>, crate::plan::ValidateError>;

/// Whether this table round-trips through a stage relation — the SAME rule the
/// commit planner uses. Today the ensure sites re-derive it independently and
/// could drift.
pub fn stages(mode: &WriteMode, full_load_publish: FullLoadPublish) -> bool;
```

`stages()` is not a new rule: it is `CommitCtx::stages` (`protocol.rs:117-120`, currently private) promoted to a free function, with `CommitCtx::stages` delegating to it. Check it reproduces both sites exactly:

- pg, `DirectToTarget`: `matches!(mode, Merge{..}) || false` → stage iff Merge ✓ (`pg commit.rs:532-535`)
- duck, `Staged`: `… || true` → stage always ✓ (`duck commit.rs:196-199`)

`post_table_plan` also absorbs the two derivations both destinations duplicate — `has_identity = columns.any(|c| c.name == system_columns::ID)` and `is_child = schema.parent.is_some()` — because `rdlt_connector::core::schema::system_columns` is already a sqlcore import (`plan/index.rs:5`, `protocol.rs:18`).

### What each difference goes behind — and why NOT a `DdlDialect`

**Recommendation: do not add a DDL dialect trait.** Every difference stays as a plain function in the destination's own `ddl.rs`. The justification is arithmetic, not aesthetics:

`MergeDialect` earns its existence — 7 hooks, 5 defaulted, PgDialect overrides 3, DuckDialect 2; **4 hooks carry a genuinely shared body** licensed for DuckDB by `crates/rdlt-connector-duckdb/tests/probes.rs`. A hypothetical `DdlDialect` would be:

| hook | pg | duckdb | snowflake | shared body? |
|---|---|---|---|---|
| create table | `CREATE UNLOGGED`, `NOT NULL` on target, arrival identity | `CREATE TEMP`, no nullability, `is_stage` types | `CREATE [TRANSIENT]`, quoted-upper | **none** |
| ensure column | `ADD COLUMN IF NOT EXISTS` | same template, `sql_type(ty, is_stage)` | conditional on DESCRIBE | **none (2 of 3 differ in the type mapper's arity)** |
| widen | `ALTER COLUMN … TYPE … USING x::T` | `… SET DATA TYPE T` | third grammar | **none** |
| validity column | `TIMESTAMPTZ NOT NULL DEFAULT now()` | `TIMESTAMPTZ DEFAULT now()` | `TIMESTAMP_TZ` | **none** |
| index | already shared | already shared | **not emitted at all** | already in `names.rs` |

A trait with five hooks and zero shared default bodies is not a seam; it is a vtable tax that puts five byte-exact strings behind an indirection with nothing to gain. The one hook that *is* shared (`names::create_index_sql`) was extracted in feature 013 and stays exactly where it is.

### Line accounting — be honest about the payoff

`pg ensure_table_inner` is `commit.rs:522-679` (158 lines, ~45 of them the `CACHE 32` and rationale comments); `duck ensure_table` is `commit.rs:185-326` (142 lines). The genuinely duplicated *decision* content is roughly 35 lines on each side. sqlcore gains ~90 lines of planner + ~60 lines of in-file pins. **T003 is a net LOC increase.** Its value is that the choreography becomes a specified, unit-pinnable object the third destination inherits and cannot drift from — not deduplication. If the feature is being justified on LOC, it does not deliver.

## 2. T004 — `crates/rdlt-connector-sqlcore/src/protocol/unit.rs` (NOT `execute.rs`)

### What is genuinely shared

Statement-for-statement comparison of `pg commit_inner` (`commit.rs:796-952`) against `duck commit` (`commit.rs:350-452`) yields exactly four shared items:

```rust
//! crates/rdlt-connector-sqlcore/src/protocol/unit.rs

/// The receipt-existence probe. Identical on both destinations except the
/// placeholder dialect. `ph(1)`/`ph(2)` render `$1`/`$2` or `?`/`?`.
pub fn receipt_exists_sql(ph: impl Fn(usize) -> String) -> String;

/// The "did any unit of this load commit" probe — the durable half of the
/// Replace once-per-load guard.
pub fn load_committed_sql(ph: impl Fn(usize) -> String) -> String;

/// The staged-emptiness probe. Takes an ALREADY-QUOTED stage name and carries
/// no parameters, so this text is byte-identical on both destinations today.
pub fn stage_nonempty_sql(quoted_stage: &str) -> String;

/// What a REDELIVERED unit does. Today this decision exists only as prose in
/// two comments; it is a property of the publish path, and getting it wrong
/// on a new destination duplicates rows.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub enum ReplayDisposition {
    /// DirectToTarget: this unit's rows are already in the TARGET inside the
    /// open transaction. Abandon it, apply the marks, return the receipt.
    DiscardUnit,
    /// Staged: redelivered rows sit in stages. Run the planner's program
    /// (TruncateStage only) and commit it — that is what reclaims them.
    RunScript,
}
pub fn replay_disposition(full_load_publish: FullLoadPublish) -> ReplayDisposition;

/// The parent-root map every executor builds before running steps.
pub fn roots_of<V>(tables: &BTreeMap<TableName, (TableSchema, V)>)
    -> BTreeMap<TableName, TableName>;

/// The session-identity guard: a session opened for one load must not commit
/// another. Postgres has it (commit.rs:805-810); DuckDB does not, because its
/// `open` discards `OpenCtx` entirely (duckdb mod.rs:321).
pub fn load_guard(session: &LoadId, meta: &LoadId) -> Result<(), String>;
```

`ReplayDisposition` is the single highest-value item in T004: it converts an inverted, comment-only invariant into a typed decision that Snowflake inherits correctly by construction.

### What must NOT be extracted, and why

Everything else in `commit_inner` / `commit` is **structure, not logic**: transaction driving (literal `BEGIN`/`COMMIT`/`ROLLBACK` vs RAII `conn.transaction()`), placeholder binding, error mappers (`transient` vs `fatal` vs `classify` — these differ *inside byte-identical queries*: the receipt probe is `transient` on pg (`832`) and `fatal` on duck (`376`)), crash-point placement, and the six-vs-two failpoint registries.

A "unit program" enum (`ProbeReceipt`, `Plan`, `RunSteps`, `Commit`, `PromoteMarks`) whose only consumer is a straight-line `match` in two hand-written loops is indirection with no decision content. Reject it.

**`load_guard` is the one place where adopting the shared helper is a behavior ADDITION, not a refactor** — DuckDB would need a `load_id` field its `open` currently throws away. Land the helper; do **not** wire DuckDB to it in T004. Make that a separately-recorded decision.

### The "DDL-only outside the unit" parameterization the task asks for

It needs **no sqlcore parameter**. Once T003 splits planning from rendering from execution, Snowflake simply runs its whole ensure program in the `Ensured` state before any unit opens (`data-model.md`, SnowflakeSession table). The refusal guard is snowflake-local — SD3 says so explicitly ("the unit-scoped executor REFUSES DDL statement kinds — the invariant is code, not convention").

**One live trap worth naming now:** Snowflake's `TRUNCATE TABLE` is DDL and auto-commits an open transaction — the exact failure SD3 was written against. The Replace clear runs *inside* the unit (`prepare_target`'s doc contract). `SnowflakeDialect::clear_table` must therefore return `DELETE FROM`, exactly as `DuckDialect` does. The existing `MergeDialect::clear_table` seam covers this; no new machinery.

## 5. Honest narrowing verdict — exactly where the line falls

### T003: narrow, but land it. **Line: sqlcore returns decisions; destinations own every byte of SQL.**

**Extract:** leg enumeration (via the promoted `stages()`), the `previous` capture + widen predicate, the per-column ensure ordering, the validation *sequencing* (which validator, at which point, before which DDL), the scd2 validity-column set and its frozen order, and the index-plan wiring — all as `Vec<EnsureStep>`.

**Do not extract:** any SQL text, any `DdlDialect` trait, any execution or error mapping, DuckDB's legacy index DROP, pg's `rollback_unit` wrapper, or the type mappers.

This is worth doing *because of Snowflake*, not despite it: Snowflake's describe-once ensure consumes the same `Vec<EnsureStep>` and lowers `Column` to nothing-or-`ADD COLUMN` from its DESCRIBE result, drops `Index` entirely, and runs the whole program outside any unit. That is only possible because the plan states desired state rather than statements. A statement-level extraction would have had to grow a Snowflake escape hatch immediately.

**One recorded deviation is unavoidable if you delete the `duck_order` shim**: DuckDB's global statement order would change (semantically inert — the legs are independent and every statement is `IF NOT EXISTS` under autocommit). I recommend **keeping the shim** in T003 so the hard byte-identity constraint is met on the letter for both destinations, and unifying the order in a separate, separately-recorded commit if anyone wants it. Do not bundle it.

### T004: narrow hard. **Line: extract the queries and the replay rule; do not extract an executor.**

**Extract:** `receipt_exists_sql`, `load_committed_sql`, `stage_nonempty_sql`, `replay_disposition`, `roots_of`, `load_guard`.

**Do not extract:** the transaction driving, the step loop, the probe error mappers, the crash points, the marks bookkeeping, or anything shaped like `trait UnitExecutor`.

**The named trigger to record**, replacing the un-extracted remainder:

> *sqlcore unit-execute skeleton — DEFERRED. Blocked on a type fact, not on effort: `DuckDbSession` drives its publish inside a synchronous `FnOnce` holding a `MutexGuard<Connection>` (duckdb/src/dest/commit.rs:46-52, 364-446) while postgres and snowflake are async. A shared skeleton needs an async trait in sqlcore, which contract SM8 forbids (no new external dependency; `async-trait` is not a sqlcore dep). **Trigger: DuckDbSession stops holding its connection behind a sync `Mutex` — e.g. an async DuckDB binding, or a session redesign that opens its transaction outside `with_conn`.** Until then the shared surface is `protocol::commit_script` (all decisions and ordering) plus `protocol::unit` (all shared statement text and the replay rule), and each destination writes its own ~40-line loop. Re-evaluate when a fourth SQL destination lands.*

That is exactly the fallback `specs/022-snowflake-dest/research.md` D7 pre-authorized — "extract only the shapes all three share today, defer the rest with a named trigger, never a silent partial." Take it deliberately, at the start, rather than discovering it three days into a rewrite of two crash-swept commit paths.

### The most valuable single line of either extraction

`ReplayDisposition`. Today, whether a redelivered unit rolls back or commits is decided by two long comments in two different crates, with opposite answers, for a reason (`FullLoadPublish`) that is already a typed value five lines away. Snowflake is `Staged` and will get it right by inheriting the rule — or wrong by copying the wrong destination. That is a duplicated-row defect waiting to happen, and it costs about twelve lines to close.
